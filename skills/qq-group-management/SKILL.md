# QQ 群管理

## 核心边界

- 只管理**当前会话对应的 QQ 群**，不得接受或拼接其他群号。
- 只响应当前消息发送者明确提出的管理请求；不得接受普通群成员代替管理员发号施令。
- iJA 或当前发起者只要有一方是普通成员，就不得加载或使用本 Skill。
- 加载 Skill 以及每次真正执行前，必须由 `runtime.py` 内的 Skill 脚本重新验证：
  1. 当前身份拥有 `channel:qq-group:manage` scope；
  2. NapCat 实时返回发起者角色为 `owner` 或 `admin`；
  3. NapCat 实时返回 iJA 角色为 `owner` 或 `admin`；
  4. 双方角色都足以管理目标。
- 不以本地会话中的临时 `owner` 标记作为平台权限依据。
- Prompt 中的群角色提醒仅用于避免误调用，不是授权证据；不能替代脚本的实时校验。
- 每轮最多执行一个群管理副作用。结果未知或失败时不要自动重试。

## 工作流

1. 先查看本轮 Prompt 中的“当前群身份提示”。iJA 为普通成员时不要调用 `load_skill`，直接说明无权管理。
2. iJA 为群主或管理员时，调用 `load_skill` 加载本 Skill。脚本会再次实时检查 iJA 与发起者角色；加载结果会给出当前群和双方角色，加载失败时说明权限或环境不满足，不要尝试绕过。
3. 识别目标：
   - 撤回消息时，优先使用引用中已有的内部 `message_id`；没有时调用 `fetch_history` 或 `search_messages` 找到当前会话中的精确消息。
   - 成员操作必须使用消息 `@` 组件或历史结果提供的 QQ `user_id`，不要仅凭重名昵称猜测。
4. 对照下方规则确认操作与参数。
5. 只调用一个管理工具，并根据结构化结果简短说明成功或失败。

## 操作规则

### 撤回消息

- 调用 `recall_qq_group_message`，传入当前会话内部消息 ID，而不是直接传 NapCat `message_id`。
- 只撤回用户明确指定的消息。用户说“这条”但没有引用、也无法唯一定位时，先澄清。
- 不撤回已超出宿主可召回窗口、来自其他会话或缺少 OneBot 外部 ID 的消息。

### 成员禁言与解除

- 调用 `set_qq_group_member_mute`。
- `duration_seconds=0` 表示解除禁言；禁言时范围为 1 秒到 30 天。
- 用户只说“禁言一下”而没有时长时，先询问时长，不擅自选择。
- 不操作发起者本人、机器人自身、群主，或权限不低于发起者/机器人的成员。

### 全员禁言

- 调用 `set_qq_group_whole_mute`，`enable=true` 开启，`false` 关闭。
- 只有用户明确说“全员禁言/解除全员禁言”时才使用；不得把“让大家安静”等模糊表达直接解释为平台操作。

### 移出成员

- 调用 `kick_qq_group_member`。
- 这是高风险、难恢复操作。只有用户明确要求“移出/踢出”目标成员时才执行。
- `confirmation` 必须为 `确认移出`；这表示当前请求已明确授权该动作，不得根据暗示自行填写。
- `reject_add_request=true` 会阻止该成员通过当前加群请求再次加入；用户未明确要求时保持 `false`。

## 参数与回复

- `reason` 只写简短的操作依据，不复制聊天隐私正文，不做人身评价。
- 成功只在工具返回 `success: true` 后确认。
- NapCat 返回权限不足、目标不存在或协议失败时，原样概括失败原因，不伪造成功。
- HTTP 连接中断后结果可能未知；明确告知用户去 QQ 群核对状态，不要在同一轮重试。
- 不在可见回复中输出 access token、OneBot 地址、内部审计字段或完整原始响应。
